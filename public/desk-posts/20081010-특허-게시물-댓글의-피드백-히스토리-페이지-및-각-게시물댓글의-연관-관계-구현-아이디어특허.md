**제목 : 게시물 / 댓글의 피드백 히스토리 페이지 및 각 게시물/댓글의 연관관계 구현**

**범위 : 다른 플랫폼의 다양한 형태의 게시물들을 가지고 있는 서비스의 집합을 가진 서비스**
** **

**문제점 :** 포탈내에 거대한 서비스를 이용하는 사용자가 뉴스, 블로그등 다양하며 다른 서비스를 이용하며 댓글혹은 포스트를 작성하지만, 시간이 지난후에 어떤 페이지에 무엇을 작성했는지 찾기도 어렵다.
그 기능이 있다하더라도, 블로그, 카페등 독립적인 서비스에서만 운용하고 있으며 종합적인 관리가 불가능하고, 기술적으로도 각 서비스들이 각자 구현을 해야한다.

**해결방법 :**
포탈내의 모든 이동경로를 아는것도 의미가 있지만, 사용자에게는 자신이 유의미 있다고 생각하는것에는 주로 댓글을 다는 형태로 웹페이지의 중요성에 대한 증거를 남긴다.
이러한 입력행위에 관한 행위를 글쓰기 히스토리라는 서비스 DB에 기록하고, 그 행위에 대한 다른 사용자의 피드백또한 DB에 등록시켜 사용자에게 보여준다.

**목적 :**
사용자가 의미있다고 생각했으나 시간이 지남에 따라 묻혀서 찾기 어려워지는 페이지의 접근도를 높이고,사용자간의 한가지 주제에대한 지속적인 커뮤니티를 유지하도록 해준다.

**방법 :**
**1) ****포탈내의 모든 웹페이지는 고유한 페이지 URL을 갖도록 만든다.**
: 히스토리를 가지고 페이지로 이동이 가능하도록 해주기 위함
- 특정 URL을 웹브라우져에 입력시 자신이 작성하던 당시의 게시물 혹은 댓글로 이동할수 있다.

**2) ****포탈내에서 댓글을 남기거나, 새로운 게시물, 혹은 포스트 같은 새로운 데이터 업로드 행위를 했을때 자신의 히스토리 레코드를 남기고 연관 히스토리 레코드의 기록을 변경한다.**
- 히스토리 DB에 현재의 페이지로 이동가능한 URL과, 히스토리ID, 사용자 식별자를 남긴다.
- 히스토리 DB의 연관 레코드가 있을경우, 변경 정보를 전파한다.
: 특정 포스트에 댓글을 다는 행위를 했을 경우, 그 포스트에 댓글을 다는 행위의 모든 사용자의 히스토리에 변경정보를 전파한다.

ex) 게시물1 에 10개의 댓글이 달렸고, 10개중 1개의 댓글에 또 다시 댓글의 댓글을 달았을 경우
2.1) 자신의 히스토리에 삽입 정보 남김
2.2) 자신이 직접 댓글을 남긴 댓글은 1단계의 연관 단계를 가진것을 전파
2.3) 자신이 댓글을 남긴 게시물1의 9개의 나머지 답글의 히스토리에는 3단계의 연관관계 전파
2.4) 자신이 댓글을 남긴 게시물1의 히스토리에는 2단계의 연관관계 전파

- 각 댓글과 게시물에 대한 연관관계 정보를 갱신하기 위해서 히스토리 서비스로 URL이나 XML을 통해

[게시물1의 히스토리 아이디 - 자신이 댓글을 단 댓글의 히스토리 아이디 - 자신이 작성한 댓글의 댓글의 히스토리 아이디]정보를
히스토리 서비스로 날려준다.

히스토리서비스에서는 위의 정보로 2.1,2.2,2.4)를 전파하며
2.3)의 연관관계는 2.2)혹은 2.3)이 갱신되는 정보를 이용하여 갱신한다.

* **이러한 게시물의 연관관계에 따라 게시물의 갱신정보가 전파됨이 특징이다.**

댓글의 하위 1단계는 댓글의 댓글이다.

**Title : Implementation of Feedback History Page for Posts/Comments and Interrelationships of Each Post/Comment**
 
**Scope : A service with a collection of services that have various forms of posts from different platforms**
 
 
**Problem :** Users utilizing various large services within a portal, such as news and blogs, write comments or posts across different services, but after some time, it becomes difficult to find what they wrote on which page.
Even if such a function exists, it operates only within independent services like blogs and cafes, making comprehensive management impossible, and technically, each service has to implement it individually.
 
**Solution :**
While knowing all navigation paths within a portal is meaningful, users primarily leave evidence of a webpage's importance by commenting on what they consider significant.
Such input actions are recorded in a service DB called 'writing history,' and feedback from other users on those actions is also registered in the DB and shown to the user.
 
**Purpose :**
To increase accessibility to pages that users considered meaningful but became difficult to find over time, and to maintain continuous community among users on a single topic.
 
 
**Method :**
**1) ****Ensure all webpages within the portal have a unique page URL.**
 : To enable navigation to the page using its history.
 - When a specific URL is entered into a web browser, users can navigate to the post or comment they were writing at that time.
 
**2) ****When a user leaves a comment, creates a new post, or uploads new data like a post within the portal, their history record is created, and related history records are updated.**
 - The URL for navigating to the current page, History ID, and User Identifier are recorded in the History DB.
 - If there are related records in the History DB, change information is propagated.
  : For example, when a comment is made on a specific post, change information is propagated to the history of all users who commented on that post.
 
   ex) If Post 1 has 10 comments, and a comment-on-a-comment is made on one of those 10 comments:
     2.1) Insertion information is left in one's own history.
     2.2) The comment directly made by the user propagates a 1-level association.
     2.3) The history of the remaining 9 replies on Post 1 (where the user commented) propagates a 3-level association.
     2.4) The history of Post 1 (where the user commented) propagates a 2-level association.
 
   - To update association information for each comment and post, via URL or XML to the history service:
     
     Information [History ID of Post 1 - History ID of the comment the user replied to - History ID of the comment-on-a-comment written by the user]
    is sent to the history service.
 
    The history service propagates 2.1, 2.2, and 2.4 with the above information,
    and the association of 2.3) is updated using the information from 2.2) or 2.3) being updated.
 
   * **A characteristic feature is that post update information is propagated according to these post associations.**
    Therefore, change information for root posts (posts, articles, or blogs) tends to be much more frequent.
   - According to these association relationships, for a blog, the 1st lower level is post creation,
      for a post, the 1st lower level is a comment.
      For a comment, the 1st lower level is a comment-on-a-comment.
 
    - Information about posts (comments) at the same level being attached to an upper post (comment) can also be stored.
      => When another comment is added to a post that has been commented on.
      => When another post of the same level, not a reply, is created on a bulletin board.
      
     * History ID Structure
For speed, the History ID structure can be designed to include the parent ID within the ID itself, allowing the parent's associated ID to be identified just by looking at the ID.
Comment ID [Parent URL - Parent Service ID - Parent Board ID - Parent Post ID - Comment ID]
 
* Actions occurring upon insertion
1. Propagation to each parent History ID: Information that a post/comment has been inserted below.
2. In special cases, propagation to History IDs in the same category: Another comment has been added to the post I commented on.
 
** DB Information
History ID : History Identifier
Parent History ID : Tracks history associations
Original Author : Owner
Original Creation Date : Original Time
Number of Child History IDs : Number of direct replies
Child History ID Update Time
Number of Descendant History IDs : Total number of comments under the written post
Descendant History ID Update Time
Number of Sibling History IDs : Number of posts on the same board written by the user
Sibling History ID Update Time
Update Status
-- Information for History Deletion ---
Creation Date Expiry Time
Update Time Expiry Time
 
* Since the number of data points is meaningful, all information UPDATEs occur upon Insert or Delete of new posts.
  : Modified posts are not reflected.
 
 
 
 
**3) ****When another user creates a related history record, one's own History DB is updated according to 2).**
 
 - Example of modify information
  1) For posts, guestbooks : A comment has been added. A reply has been added. A trackback has been created.
     - In this case, the user who made the comment also leaves a record in their history.
 
  2) For comments : A comment-on-a-comment has been added.
  
**4) ****The user views the history page. : User utilization**
 - Displays information from the History DB.
 
   Original Creation Time | Content | New Comment/Trackback | New Comment Time
   
 - Can be sorted by each item. (What is usually meaningful to the user is the new comment time.)
 
 - If the data capacity of the History DB becomes an issue
** **
**  * ****History Deletion Priority**
**  1) ****If there is no new comment time or a certain period has passed.**
**  2) ****If the original creation time has passed a certain period, only when condition 1) applies.**
 
 - When clicking on a history entry, it navigates to the corresponding comment or post. If a new comment is added there,
   the original creation time does not change, one's new comment/trackback is added, and the new comment time is updated.
