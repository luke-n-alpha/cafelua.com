****1. 제목 : 이동성의 차별성이 있는 N스크린 환경하의 IM과 3g유저 접점선택 방법**
**2. 최초 작성일 : 2011년 4월 29일**
**2. 배경**유저는 타블릿과 스마트폰과 pc의 다수의 n스크린환경에 있다. 이때 n스크린에 제공되는 3g와 IM같은 유저커뮤니케이션도구에서 메시지를 어떤 스크린에 보낼지에 대한 고민이다. 현재는 3g의 경우에는 n스크린을 지원하지 않고, IM의 경우에는 양쪽에 모두 보내기, 혹은 유저의 선택에 의해 하나의 기기에 접속됬을때 다른 기기를 로그아웃 시키기, 하나의 기기에 우선권을 설정하기가 있다.

**3. 근거리 센서/통신망을 이용한 n스크린의 더블 Usim의 3g call 우선순위 문제**갤럭시패드와 아이폰을 가지고 있는 유저에게 전화를 걸었을때 어떤 기기에 call을 울릴까 하는 고민이다. 현재는 각 기기에 별도의 3g usim을 사용하여 두개의 번호를 따도록되어있다.그러나 이는 두개의 usim에 같은 번호를 할당한 경우를 가정한다. 혹은 실제로 다른 두개의 번호를 할당했지만, 이 두개가 같은 그룹이란 별도의 정보를 두는 방법도 포함한다. 문제는 N스크린 혹은 N개의 번호라 하더라도 1명의 유저라는 정보가 있고 어떤 기기에 call을 울릴까 하는 문제이다.**
****1) 사용자 액션 중인 기기가 있을때**N개의 기기중 1개의 기기가 사용자 액션이 있고 나머지가 서스팬드모드에 있는경우, 액션이 있는기기에 call을 울린다. 사용자가 집에 있더라도 스마트폰의 액션이 있다면 패드보다 스마트폰을 울리도록 한다. 액션이란 실제 사용자가 터치를 하며 기기를 구동중인 상태를 의미한다.
**2) 기기가 근거리에 있을 때**사용자 혹은 최초가입시 미리 설정된 기기의 우선순위에 따라 call을 울린다. 이때 설정되는 우선순위의 기준은 이동성이 낮은 기기순이다. 근거리 여부는 두개의 기기가 같은 wifi ap에 연결되어 있거나 혹은 스마트패드에 스마트폰이 블루투스로 연결되어 있거나 gps의 위치가 일정 범위내에 있거나, 혹은 타 근거리라는 것을 알 수 있는 어떤 수단이던 상관이 없다. 사용자가 집에서는 스마트패드에서 전화를 받을 수 있는 조건이 된다.**
****3) 기기가 원거리에 있을때**위의 지근거리에서 두개의 기기가 벗어났을때, call은 이동성이 높은 기기 순으로 call을 울린다. 패드를 집에두고 스마트폰을 밖으로 나갔을때, 스마트폰의 call을 울릴수 있는 기준이 된다.
**4. IM에의 적용**- IM의 경우에도 pc와 스마트폰, 웹에서 모두 접속되어 있을수가 있다. 이때의 경우를 가정해본다. 일반적으로는 IM은 n스크린은 모든 기기에 동일하게 뿌려도 크게 문제는 없다. 하지만, 리소스의 낭비가 존재할 수도 있고, 최초 대화요청시, call개념으로 기기에 큰 알람을 날릴수도 있고, 혹은 Mvoip를 탑제할수도 있기에 이를 가정한다.

**1. Title: IM and 3G User Contact Point Selection Method in an N-Screen Environment with Mobility Differentiation**
**2. First Draft Date: April 29, 2011**
**2. Background**
Users are in a multi-N-screen environment with tablets, smartphones, and PCs. At this time, the concern is which screen to send messages to from user communication tools like 3G and IM provided in the N-screen environment. Currently, 3G does not support N-screens, and for IM, options include sending to both, logging out other devices when one device is connected based on user selection, or setting priority for one device.

**3. 3G Call Priority Issue for Dual USIMs in N-Screens Using Proximity Sensors/Communication Networks**
This is about which device should ring when a call is made to a user who has a Galaxy Pad and an iPhone. Currently, each device uses a separate 3G USIM, resulting in two numbers. However, this assumes the case where the same number is assigned to two USIMs. Alternatively, it also includes a method of assigning two different numbers but having separate information indicating that these two belong to the same group. The problem is that even with N-screens or N numbers, there is information that it's one user, and the question is which device should ring.
**1) When there is a device with user action**
If one of N devices has user action and the others are in suspend mode, the call rings on the device with action. Even if the user is at home, if there is action on the smartphone, it should ring the smartphone rather than the pad. Action refers to the state where the user is actually touching and operating the device.
**2) When devices are in close proximity**
The call rings according to the priority of devices pre-set by the user or at initial subscription. The criterion for setting priority at this time is in order of devices with lower mobility. Proximity can be determined by whether two devices are connected to the same Wi-Fi AP, or if a smartphone is connected to a smart pad via Bluetooth, or if their GPS locations are within a certain range, or any other means that can indicate proximity. This allows the user to receive calls on the smart pad when at home.
**3) When devices are at a distance**
When the two devices move out of the close proximity mentioned above, the call rings on devices in order of higher mobility. This becomes the criterion for ringing the smartphone when the pad is left at home and the smartphone is taken outside.
**4. Application to IM**
- In the case of IM, it can be accessed from PCs, smartphones, and the web. Let's assume this scenario. Generally, for IM, there isn't a big problem with broadcasting to all N-screen devices equally. However, there could be resource waste, a large alarm might be sent to devices like a 'call' concept during the initial chat request, or MVoIP might be integrated, so we assume these possibilities.
1) Prioritize devices with user action - Same as 3.1)
2) If all are inactive and in keep-alive mode - Prioritize devices with higher mobility, like in 3.3)
Order of mobility: PC > Web > Mobile App
