**1. 제목 : 검색결과 변동 리포트 서비스**

**2. 배경 :** 네이버 중고나라에서 특정 물품이 나오기를 대기하고 있는중에 매번 해당 게시판으로 가서 검색결과를 확인해야 하는 번거로움이 있었다. 이를 자동으로 해주면서 검색결과가 변동되었을때만 리포트해주는 범용 엔진을 구상해본다.

**3. 최초 작성일 : **2010년 7월 8일

**4. 개념
**1) 검색 키워드 : 유저가 찾고자 하는 대상의 키워드, 유저의 쿼리
2) 검색 대상 : 인터넷 상에 존재하는 검색 대상 개체, 이 개체는 하나의 고유주소를 갖는다. 특정 게시판, 혹은 사이트, RSS등이 될수 있다.
3) depth : 검색대상에서 노출된 링크들을 통해 검색할 재귀적 깊이
4) 검색빈도 : 검색기가 해당 대상을 재검색할 시간차

**5. 시나리오
5.1. 포탈외의 일반 사이트
**: 웹크롤러가 검색빈도에 따라 검색대상에 접근하여 검색결과를 취합해오는 방식
1) 유저는 서비스에 검색대상과 검색키워드를 입력한다.
2) 서비스 서버는 해당 검색대상에 접근하여 사전에 설정된 depth에 따라 크롤링을 한다. 그리고 해당 검색 키워드로 검색된 검색 결과를 다시 만들어 서비스 서버에 저장한다.
3) 시스템 혹은 유저가 설정한 검색빈도에 따라 서비스 서버는 재 크롤링을 시도하여 이전 검색결과와 비교한다.
4) 검색결과가 변화가 있는 경우 유저에게 이메일, sms등을 통해 알려준다.
5) 유저는 이를 통해 찾고자 하는 것이 새로 등록되었음을 인지하고 검색대상으로 바로 접근하거나 서비스 게시판으로 가서 검색결과를 조회한다.

**5.2 포탈내의 게시판, 카페, 블로그
**: 내부 api를 통해 검색결과를 조회해오는 방식
- 기본적으로 시나리오는 3.1과 동일하나 웹크롤러가 해당 사이트에 방문하는 것이 아니라 내부 api를 통해 검색결과를 받아와 비교한다는것이 다르다.

**5.3 RSS를 지원하는 사이트
**: 크롤링을 Rss로 대치할 수 있다.

**5.4. 검색창을 붙인 사이트
**: 구글검색창을 붙인 사이트의 경우, 해당 검색창으로 직접 쿼리를 날리고 검색결과를 비교하여 리포트할 수 있다. 검색색인api를 제공하는 사이트에 적용가능하다.

**6. 등록시 검색방법 자동탐색
**외부 사이트 등록시 해당사이트를 분석하여 어떤 방식으로 검색을 할지를 판단할 수 있다.

**1. Title: Search Result Change Report Service**

**2. Background:** While waiting for a specific item to appear on Naver Joonggonara (used item marketplace), there was the inconvenience of having to go to the relevant bulletin board every time to check the search results. I envision a general-purpose engine that automates this process and only reports when search results change.

 
**3. First Draft Date:** July 8, 2010

**4. Concepts**
1) Search Keyword: The keyword for the item the user is looking for, the user's query
2) Search Target: A searchable entity existing on the internet; this entity has a unique address. It can be a specific bulletin board, website, RSS feed, etc.
3) Depth: The recursive depth to search through links exposed from the search target.
4) Search Frequency: The time interval at which the search engine re-searches the target.

**5. Scenarios
5.1. General Websites (outside of portals)**
: A method where a web crawler accesses the search target according to the search frequency and collects search results.
1) The user inputs the search target and search keyword into the service.
2) The service server accesses the search target and crawls according to the pre-set depth. It then re-generates the search results for the given search keyword and stores them on the service server.
3) According to the search frequency set by the system or the user, the service server attempts to re-crawl and compares the results with previous search results.
4) If there is a change in the search results, the user is notified via email, SMS, etc.
5) The user, recognizing that what they were looking for has been newly registered, can directly access the search target or go to the service bulletin board to view the search results.

**5.2. Bulletin Boards, Cafes, Blogs within Portals**
: A method of retrieving search results via internal APIs.
- Basically, the scenario is the same as 5.1, but the difference is that the web crawler does not visit the site; instead, it receives and compares search results via internal APIs.

**5.3. Sites Supporting RSS**
: Crawling can be replaced by RSS.

**5.4. Sites with an Embedded Search Bar**
: For sites with an embedded Google search bar, queries can be sent directly to that search bar, and search results can be compared and reported. This is applicable to sites that provide search indexing APIs.

**6. Automatic Search Method Detection upon Registration**
When registering an external site, the system can analyze the site to determine how to perform the search.
