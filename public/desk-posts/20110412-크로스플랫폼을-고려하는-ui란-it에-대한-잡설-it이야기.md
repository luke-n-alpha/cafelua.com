**1. 특정OS의 UI만을 따랐을때 혼란스러운 유저

** 저는 아시다시피 안드로이드 유저입니다. 그런데 가끔 어떤 앱을 쓰다보면 버튼을 해메는 경우가 존재하는데 이러한 앱들의 공통점은 상단의 좌,우에 버튼이 배치되어있다는 점입니다. 이후에 아이폰을 조금 쓰다보니 그 혼란의 원인을 알겠더군요. 아이폰은 맨 상단의 우측은 보통 sumbit버튼이 존재하고 상단좌측에는 cancel혹은 뒤로가기 버튼이 존재합니다. 이는 ios에서 제공하는 기본 confirm윈도우의 모습인것 같습니다.

{{IMG:1}} 그러나 이러한 앱의 크로스 플랫폼을 구현하기 위해서는 무조건적인 하나의 os특성을 따라가기보다는 보다 넓은 시선이 필요해보입니다. 모바일 단말은 낮은 스펙, 그리고 하드웨어버튼이 존재하지 않을수도 있다는 점, 각각의 os에서 제공하는 ui의 가이드가 상이할수 있다는 점을 고려해야합니다.

**2. 애플의 최상단 버튼의 어색함

**처음 이야기한 뒤로가기와 확인이 위치한 ui를 이야기하자면 애플의 이러한 ui는 웹과 윈도우즈유저에게 익숙하지 않습니다. 왜냐하면 대게는 컨텐츠를 읽고 action을 결정하는데 때문에 버튼은 컨텐츠의 하단에 위치합니다.  {{IMG:2}}따라서 애플의 상단 버튼 UI는 타 OS유저들에게는 혼란을 줄 수 있다는 이야기죠.
사용자의 시선은 좌에서 우로, 위에서 아래로 간다는 점에서, 애플의 UI는 옳지 않아 보입니다. 상단에는 메뉴가, 아래가 Confirm이 맞지 않나 싶은데 일반적으로 스마트폰에서는 거꾸로입니다. (초기 Palm기반이 상단이 메뉴였습니다.)

** 3. 안드로이드의 하드웨어 버튼의 맹신**

그럼 이번엔 안드로이드로 돌아와서 뒤로가기 버튼 이야기를 해보죠. 안드로이드 OS는 하드웨어 버튼이 존재합니다. 메뉴버튼과 뒤로가기 버튼인데, 이를 고려하여 터치로 뒤로가기나 메뉴를 숨겨둔다고 가정해보죠. 이를 다시 아이폰으로 옮겼을때는 문제가 생깁니다. 이후 블랙베리나 바다로 옮겨갔을때는 어떨까요? 뒤로가기 버튼이 필요하다면 명시적으로 화면상에 출력을 해줘야합니다.

**4. UI의 가이드라인은 웹경험이 아닐까?
**

이후 타블릿시대가 오더라도 마찬가지입니다. 크로스플랫폼을 고려하고 있다면 맹목적으로 Os가 제공하는 템플릿 UI를 사용하기전에 이러한 부분을 한번즈음은 고려해봐야할것입니다.

저는 개인적으로 올해 내년즈음의 모바일의 가장 큰 이슈는 크로스플랫폼이 되지 않을까합니다.

**1. Users Confused by UI that Follows Only a Specific OS

** As you know, I am an Android user. However, sometimes when I use certain apps, I find myself fumbling for buttons, and the commonality among these apps is that their buttons are placed at the top left and right. After using an iPhone for a while, I understood the cause of that confusion. On iPhones, the top right usually has a submit button, and the top left has a cancel or back button. This seems to be the appearance of the default confirm window provided by iOS.

{{IMG:1}} However, to implement cross-platform for such apps, a broader perspective seems necessary rather than unconditionally following the characteristics of a single OS. Consideration must be given to the fact that mobile devices may have low specifications, may not have hardware buttons, and that the UI guidelines provided by each OS may differ.

**2. The Awkwardness of Apple's Top Buttons

** Speaking of the UI where back and confirm buttons are located as I first mentioned, Apple's UI is unfamiliar to web and Windows users. This is because users typically read content and then decide on an action, so buttons are usually located at the bottom of the content. {{IMG:2}}Therefore, Apple's top button UI can cause confusion for users of other OSes.
Considering that a user's gaze goes from left to right, and top to bottom, Apple's UI does not seem correct. It seems more appropriate for the menu to be at the top and Confirm at the bottom, but generally on smartphones, it's the other way around. (Early Palm-based devices had the menu at the top.)

**3. Blind Faith in Android's Hardware Buttons**

Now, let's return to Android and talk about the back button. The Android OS has hardware buttons. There's a menu button and a back button. Let's assume that, considering these, the back or menu functions are hidden behind touch gestures. When this is transferred to an iPhone, problems arise. What about when it's moved to BlackBerry or Bada? If a back button is needed, it must be explicitly displayed on the screen.

**4. Could Web Experience Be the UI Guideline?
**
What encompasses all of this is web experience; in fact, we are already quite familiar with such cross-platforms, and that is the web. The web has been well-used across various resolutions and environments. If the UI was simply built for the web, compatibility would be largely guaranteed. And the foundation of user experience on PCs and other devices has largely been web experience. So, if you're unsure about which UI to use, thinking about the web might give you a clearer picture.

The same applies when the tablet era arrives. If you are considering cross-platform development, you should consider these aspects at least once before blindly using the template UI provided by the OS.

Personally, I believe the biggest issue in mobile around this year and next will be cross-platform.
