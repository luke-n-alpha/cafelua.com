**1. 다양해지는 모바일 플랫폼의 환경 변화**
최근 하루가 멀다하고 쏟아져 나오는 새로운 모바일기와 플랫폼들이 쏟아지고 있습니다. 처음 아이폰이 나왔을때는 아이폰용 어플리케이션 하나 더 만들면 되겠구나 싶었지만, 2010년들어 발표된 플랫폼만 해도 도대체 몇개인지 모르겠습니다. 과연 회사들이 이 모든 플랫폼에 대응해 어플리케이션을 만들 수 있을까요? 어느 시장이 활성화 될지 예측이 어렵고 재개발 비용 또한 만만치 않습니다. 그런 모험을 할 수는 없는 노릇이고, 그렇다면 현명한 방법을 찾아야겠죠.

** 2. 정답은 웹
** 이러한 상황에서 모든 모바일 단말에서 가능한 솔루션들은 결국 웹이었습니다. 결과적으로 구글의 영향력은 더욱 강력해졌죠. 하지만 웹은 html의 한계로 인해 할 수 있는 것은 제한되어있습니다. 카메라를 이용한 솔루션들은 어떻게 처리해야 할까요? 결국 클라이언트단의 특성을 감안하면서 공통의 비즈니스 로직이나 서비스를 제공하는 모델이 필요하다는 생각이 들었습니다. 그러고보니 이에 적합한 서비스 모델이 이미있습니다.

** 3. SOA의 사상을 이용한 서비스의 분리**
넓게 보면 SOA이고 좁게보면 WOA나 웹을 통한 XML API나 OpenAPI정도로 볼 수 있습니다. 어차피 인터넷으로 모듈간 통신을 하는 이 솔루션들은 핵심 로직은 서버에서 출력하고 클라이언트나 단말마다 xml을 이용해 어떤 어플리케이션을 만들던 무관합니다. 기존의 웹사이트를 개발할때 MVC패턴으로 개발시, 일반적으로 비즈니스로직과 뷰는 한 프로젝트에 존재합니다. 그러나 라면 비즈니스로직을 수행하는 프로젝트와 뷰와 컨트롤러를 수행하는 프로젝트를 분리해 개발이 가능합니다. 이 뷰와 컨트롤러역할을 하는 것은 웹사이트일 수도 있고, 앱일수도 있죠.
{{IMG:1}}
간단히 설명해 드리면... 네이버 메일은 웹에서 보일때 다르고, 모바일사이트에서 볼때 다릅니다.
**네이버 메일**이라는 실제 DB에서 메일을 가져오거나하는 서버와, 유저와 좀 더 밀접한 역할을 하는 (웹페이지용)**네이버 웹메일 서버**, 그리고 (모바일 페이지용)**네이버 모바일메일 서버**로 나누어 개발할 수 있겠죠. 어쩌면 네이버 웹메일 서버가 따로 존재하지 않을수도 있습니다. 기존의 레가시 시스템은 이를 고려하지 않고 만들었기 때문일수도 있죠.이 경우 **네이버 메일서버(웹페이지용)**에 xml api를 만드는 것만으로도 레가시 시스템이 하나의 서비스 컴포넌트가 되어 다른 모바일 어플리케이션에 대응할 수 있을것입니다. 물론 이것이 실제 모듈을 호출하는 것이 아니므로, SOA나 WOA라고 말하긴 어렵습니다. OpenAPI란 쪽이 더 가깝습니다. 그저 사상이 투영되었다라는 정도죠.

그리고 이미 그러한 시도가 빈번하게 이루어지고 있습니다. 처음부터 나누어 개발했다면 훨씬 쉬워졌겠죠. 그리고 이렇게 놓고 보니 그동안 실효성에 의심을 받던 SOA의 사상이 **다양한 이기종 플랫폼 호환성이란 부분이 모바일이 뜨면서 가치가 크게 상승하고 있는 듯합니다.**

**4. 변화**
이 사상을 기반으로 만들어지는 서비스들 SaaS와 클라우드컴퓨팅도 자연스럽게 중요성이 더 커지겠죠. 결과적으로 가트너가 헛소리를 한것은 아닌것 같습니다.

모바일의 환경변화는 소프트웨어의 아키텍쳐에도 큰 영향을 미치기 시작하지 않았나 싶습니다.

**1. Environmental Changes in Diversifying Mobile Platforms**
Recently, new mobile devices and platforms are pouring out almost daily. When the iPhone first came out, I thought we'd just need to create one more application for the iPhone, but I don't even know how many platforms have been announced just in 2010. Can companies really develop applications for all these platforms? It's difficult to predict which market will become active, and redevelopment costs are also considerable. Such a venture is not feasible, so we must find a wise solution.

**2. The Answer: The Web**
In this situation, the solutions possible on all mobile devices ultimately turned out to be the web. As a result, Google's influence has become even stronger. However, due to the limitations of HTML, what the web can do is restricted. How should solutions that utilize cameras be handled? Ultimately, I felt that a model was needed that could provide common business logic or services while considering the characteristics of the client side. Come to think of it, a suitable service model for this already exists.

**3. Separation of Services Using the Philosophy of SOA**
Broadly speaking, it's SOA; narrowly, it can be seen as WOA, XML API via the web, or OpenAPI. These solutions, which communicate between modules over the internet anyway, output core logic from the server, and it doesn't matter what application is created using XML for each client or device. When developing existing websites using the MVC pattern, business logic and views generally reside in one project. However, it is possible to develop by separating the project that performs business logic from the project that performs views and controllers. What acts as this view and controller could be a website, or it could be an app.
{{IMG:1}}
To explain simply... Naver Mail looks different when viewed on the web and when viewed on a mobile site.
You could develop it by dividing it into a server that retrieves mail from the actual DB, called **Naver Mail**, a **Naver Webmail Server** (for web pages) that plays a role closer to the user, and a **Naver Mobile Mail Server** (for mobile pages). Perhaps a separate Naver Webmail Server might not even exist. This might be because existing legacy systems were built without considering this. In this case, simply creating an XML API for the **Naver Mail Server (for web pages)** would allow the legacy system to become a service component capable of responding to other mobile applications. Of course, since this isn't actually calling a module, it's difficult to call it SOA or WOA. OpenAPI is closer. It's merely that the philosophy is reflected.

And such attempts are already frequently being made. If it had been developed separately from the beginning, it would have been much easier. And looking at it this way, it seems that the value of the SOA philosophy, which had been doubted for its effectiveness, is significantly increasing as mobile gains prominence, particularly in the area of **diverse heterogeneous platform compatibility.**

**4. Change**
Services built upon this philosophy, such as SaaS and cloud computing, will naturally also grow in importance. As a result, it seems Gartner wasn't talking nonsense after all.

I believe the environmental changes in mobile have begun to significantly impact software architecture as well.
