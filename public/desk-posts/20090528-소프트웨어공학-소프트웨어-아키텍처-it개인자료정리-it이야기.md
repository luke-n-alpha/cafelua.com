**1. 소프트웨어 아키텍처의 개념**
** 가. 아키텍처란의 정의 (IEEE1471)**
- 아키텍처 : 컴포넌트로 구체화된 시스템의 기본적인 조직이며, 환경에 대한 관계이며, 디자인과 진화를 이끄는 원리.
** 나. 아키텍처의 주요 개념 **

| ** 개념** | **내용 ** | **실예 ** |
| --- | --- | --- |
| 도메인 | 특정 범위별 아키텍처 존재 | 소프트웨어 아키텍처, 시스템 아키텍처, 엔터프라이즈 아키텍처, 하드웨어 아키텍처 |
| 구조 | 엘리먼트간의 구조적 특성 | 하위 시스템, 프로세스, 라이브러리, 데이터베이스, 전산 노드, 레거시 시스템, 제품 |
| 작동 | 구조적 엘리먼트간의 인터랙션 정의 | UML 시퀀스 다이어그램 |
| 주요 엘리먼트에 집중 | 시스템을 추상화하여 주요 엘리먼트에 집중하고 주요하지 않은 엘리먼트는 생략, 간소화 | 요구 사항, 리스크 분석, 실행 가능한 소프트웨어 구현 |
| 스테이크 홀더의 요구사항 | 스테이크홀더간의 상충하는 요구사항들의 결정 | 엔드유저는 신뢰성,가용성,보안성을 요구하고 마케터는 경쟁력있는 기능, 비용 요구 |
| 결정을 위한 이론 | 결정에 대한 이론적 근거 제시 | 아키텍처가 리뷰 될 때와 아키텍트가 결정을 판단할 때 사용 |
| 스타일 | 비슷한 영역들을 공유하는 시스템에서 파생된 유사성 | 분산 스타일, 파이프와 필터 스타일, 데이터 중심 스타일, 규칙 기반 스타일 |
| 팀구조 | 주어진 영역을 다루는 관련 엘리먼트들의 그룹핑을 정의 | 아키텍처에 따른 소프트웨어 개발팀 구조를 정의 |

| 용어 | 내용 | 예시 |
| --- | --- | --- |
| acquirer | system을 얻는 개인 또는 기관 | 코끼리를 3년 뒤 사갈 동물원 주인 |
| system | 각 어플리케이션들, 서브 시스템들, 시스템의 집합, 제품 라임, 제품군등의 구현체 | 코끼리 |
| mission | environment 안에서 한명이상의 stakeholder 들이 의도하는 system의 사용/운영방법 | 1.5t의 귀가 크고 7km 로 뛸 수 있는 코끼리 를 키워내기 |
| environment | system에 영향을 주는 요인으로 개발, 운영, 정치등의 외부 요인등으로 시스템에 영향을 주는 요인 | 3년의 사업기간, 코끼리가 자랄 우리, 계절, 코끼리의 시세 |
| stakeholder | 한명 이상의 system에 대한 이해 당사자로 각자 다른 system에 대한 concern을 가지고 있으며 개인이나 기관 | 조련사, 동물원 주인 |
| concerns | system의 성능, 유연성, 보안, 분배, 진화등을 포함한 한명 이상의 stakeholder들에게 중요한 system의 개발이나 운영등 측면 | 조련사의 concern 은 어떻게 1.5t 까지 코끼리를 건강하게 성장 시키느냐. 동물원 주인의 concern은 이 코끼리를 샀을때 얼마만큼의 동물원 수익을 증가 시킬 수 있는가? |
| architectural description | system 구축시 environment 에 적합하도록 추천하는 수행방법으로 architecture 가 기록되는 방법 | 코끼리 조련 일지 |
| view | - 전체 시스템에 concern들의 집합의 관점 - architectural description은 다수의 view로 구성 - 특정 viewpoint 에 따라 시스템의 아키텍쳐를 표현하는 방법 - 한개 이상의 architectural model 들로 구성 | 조련사가 생각하는 코끼리가 성장하는 모습은 1st view(동적), 조련사가 생각하는 훌륭한 코끼리의 모습은 2nd view(정적) 동물원 주인이 생각하는 1.5t 짜리 귀가 크고 7km 로 뛰는 코끼리는 3rd view(정적) |
| viewpoint | view 가 만들어지거나 묘사되거나 분석되어 지는데 기준을 만드는 관점으로 view 를 표현하기 위해 어떤 언어(notation, model, product types)가 쓰여질지 결정하게 해주는 내용 - concerns을 표현하기 위한 pattern 이나 template | 조련사가 생각하는 이상적인 코끼리를 표현하는 방법 |

나. UML 4+1 View

| 관점 | 설명 (UML Diagram) |
| --- | --- |
| 유즈케이스 관점(Usecase view) | 실제 사용하는 사용자 관점 (Use-Case) |
| 설계 관점(Design view) | 요구된 기능을 제공하기 위한 시스템의 구조와 기능 관점 (Collaboration, Class) |
| 프로세스 관점(Process view) | 시스템의 동작 관점 (Activity) |
| 구현 관점(Implementation view) | 시스템의 소프트웨어와 하드웨어를 구현하는 관점 (Component) |
| 배치 관점(Deployment view) | 시스템을 구성하는 물리적인 배치 관점 (Deployment) |

다. SAD (Software Architectruure Document)
- SAD의 활용 방안 :
교육용, 의사소통 도구, 시스템 평가 분석 과정에 필요한 입력 값
- SAD작성의 7가지 지침
1) 읽는 사람의 관점에서 문서를 작성
2) 불필요한 반복 제거
3) 모호함 회피
4) 표준 체계 준수
5) 근거 작성
6) 문서를 항상 최신으로 유지
7) 목적에 맞게 작성됐는지 사후 검토

** 라. 아키텍트의 7가지 역할 (Applied Software Architecture 에 정의)**

**1. Concept of Software Architecture**
** a. Definition of Architecture (IEEE1471)**
   - Architecture: The fundamental organization of a system embodied in its components, their relationships to each other and to the environment, and the principles guiding its design and evolution.
** b. Key Concepts of Architecture **

| **Concept** | **Content** | **Example** |
| --- | --- | --- |
| Domain | Architecture exists for specific scopes | Software Architecture, System Architecture, Enterprise Architecture, Hardware Architecture |
| Structure | Structural characteristics between elements | Subsystems, Processes, Libraries, Databases, Computing Nodes, Legacy Systems, Products |
| Operation | Defines interactions between structural elements | UML Sequence Diagram |
| Focus on Key Elements | Abstract the system to focus on key elements, omitting or simplifying non-key elements | Requirements, Risk Analysis, Executable Software Implementation |
| Stakeholder Requirements | Decisions on conflicting requirements among stakeholders | End-users demand reliability, availability, security; marketers demand competitive features, cost |
| Theory for Decisions | Provides theoretical basis for decisions | Used when architecture is reviewed and when architects make decisions |
| Style | Similarities derived from systems sharing similar domains | Distributed Style, Pipe-and-Filter Style, Data-Centric Style, Rule-Based Style |
| Team Structure | Defines grouping of related elements covering a given area | Defines software development team structure according to architecture |

**  2. Relationship between Design Patterns and Architecture**
    a. Design Patterns as a Style of Software Architecture
      - Design patterns are a subset of software architecture that define the structure and operation of software.

| Term | Content | Example |
| --- | --- | --- |
| acquirer | Individual or organization acquiring the system | Zoo owner who will buy an elephant in 3 years |
| system | Implementations such as applications, subsystems, collections of systems, product lines, product families | Elephant |
| mission | Intended use/operation method of the system by one or more stakeholders within the environment | Raising an elephant that weighs 1.5 tons, has large ears, and can run 7 km/h |
| environment | Factors influencing the system, such as development, operation, political external factors | 3-year project period, enclosure for the elephant to grow, seasons, market price of elephants |
| stakeholder | One or more interested parties in the system, each with different concerns about the system, individuals or organizations | Trainer, zoo owner |
| concerns | Aspects of system development or operation important to one or more stakeholders, including system performance, flexibility, security, distribution, evolution | Trainer's concern is how to grow the elephant healthily to 1.5 tons. Zoo owner's concern is how much zoo revenue can be increased by buying this elephant. |
| architectural description | Recommended method of execution to suit the environment during system construction, how architecture is documented | Elephant training log |
| view | - A perspective on a set of concerns for the entire system - An architectural description consists of multiple views - A method of representing the system's architecture according to a specific viewpoint - Composed of one or more architectural models | The trainer's idea of how the elephant grows is the 1st view (dynamic), the trainer's idea of a magnificent elephant is the 2nd view (static). The zoo owner's idea of a 1.5-ton elephant with large ears that runs 7 km/h is the 3rd view (static). |
| viewpoint | A perspective that establishes criteria for how a view is created, described, or analyzed, determining what language (notation, model, product types) will be used to express the view - A pattern or template for expressing concerns | The trainer's method of expressing an ideal elephant |

 c. SAD (Software Architecture Document)
  - SAD Utilization Methods: 
   Educational, communication tool, input for system evaluation and analysis process
  - 7 Guidelines for SAD Creation
      1) Write the document from the reader's perspective
      2) Eliminate unnecessary repetition
      3) Avoid ambiguity
      4) Adhere to standard structure
      5) Document rationale
      6) Keep the document up-to-date
      7) Review afterward to ensure it meets its purpose

** d. 7 Roles of an Architect (Defined in Applied Software Architecture)**

1. Presenting the project's vision
2. Consultant capable of advising on core technologies
3. Decision-maker for critical issues faced by the project
4. Coaching role for architecture
5. Mediator resolving conflicts
6. Software implementation engineer
7. Advocate for the importance of architecture
