**2.     ****소프트웨어 테스트의 가치**
-       테스트의 정의 : 결함을 발견할 의도로 프로그램을 실행하는 과정
-       소프트웨어의 품질을 높임
-       소프트웨어의 추가, 변형으로 발생하는 Side effect 사전에 제거 혹은 축소
**3.     ****소프트웨어 테스트의 원리**
-       요구사항 추적성 : 결함은 고객의 요구사항을 충족 시키는데 원인이 있음
-       시험 계획은 요구 사항이 모델이 완성되는 순간에 시작
-       Pareto 원리 : 모든 결함의 80%가 20%의 취약점에서 발생한다.
-       시험은 작은 부분에서 큰 부분으로 옮겨간다.
-       완벽한 시험은 불가능하다.
-       독립된 제 3자의 시험이 더 효과적임
**4.     ****테스트의 종류**
**4.1  ****SDLC에서의 테스트**
**4.1.1      ****Water Fall 모델의 테스트**
- [ 분석 – 설계 – 구현 – 테스트 – 인수 - 유지/보수 ]
- 구현 이후의 테스트 단계 존재
- 테스트 단계에만 테스트를 수행시 분석, 설계, 구현시 문제점 발견에 어려움

*** 빅뱅 테스트 [단순 결합]**
- 각 모듈을 개별적으로 단위 테스트
- 상호간의 인터페이스에 대하여는 고려 없음
- 모든 모듈의 단위 테스트가 끝난 시점에서 한꺼번에 결합
- 대규모 시스템에서는 비효율적
- 한꺼번에 결합하여 프로그램을 테스트하여 이상한 결과가 생기는 경우 어느 모듈이 원인인가를 파악하기 어려움 즉, 모든 모듈 조사 필수
- 소규모적인 프로그램에서 모듈 구조가 잘 설계되어 인터페이스가 번잡하지 않을 경우 사용

**4.1.2.1. 화이트 박스 테스트**
-  내부의 흐름을 파악하기 때문에 WhiteBox/Glassbox 시험이라고도 불림
-  시험을 위해 절차적 설계의 제어 구조를 사용하는 시험 설계 방법
-  효율성을 중시 하고 내부를 비교적 자세히 보기 때문에 단위 테스트에 유용함

| 기본 경로 시험 | 복잡도 측정, 의도된 흐름 동작 여부 확인 | 흐름도 기호법, 순환 복잡도, 시험 사례 유도, 그래프 행렬 |
| --- | --- | --- |
| 제어 구조 시험 | 논리적 오류 파악 | 논리연산자, 논리변수, 논리괄호, 관계 연산자 |
| 루프 시험 | 루프 구조의 적합성 확인 | 단순,중첩,연결,비구조적 루프 |

**4.1.2.2. 통합 테스트와 블랙 박스 테스트**
- 시험 대상의 입력값과 출력값만을 이용하는 시험 설계 방법
- 시스템의 신뢰도에 중점

| 종류 | 설명 | 예시 |
| --- | --- | --- |
| 동등 분할 기법 | 테스트 상황을 일정 단위로 나눈 테스트 | 웹서버를 1시간 단위로 48시간 테스트 |
| 경계값 분석 | 시스템이 변하는 경계값 중심 변화 테스트 | 날짜가 바뀌는 0시 전후 1분 집중 테스트 |
| 그래프 분석 | 전체 테스트 상황의 그래프적 변이 분석 | 48시간 동안 사용자 응답 시간 그래프 변이 분석 |
| 경험적 기법 | 경험적 이상 상황 확인 | 개발자들의 습관적 실수중 하나인 SQL Injection 확인 |

**4.2  ****특수 테스트**
4.2.1       **임베디드 SW 테스트
**- HW 의존적인 테스트 필요
- 환경에 따른 테스트 필요
- HW 개발이 완료 되지 않은 중 SW테스트 하는 경우 발생 (Emulator 환경 하의 Test)
- 기존의 Application SW뿐만 아니라 Middleware와 Hardware API 까지 테스트 필요
- 테스트 실패시, SW 패치가 어려우며, Recall이 발생할 가능성이 존재함**
**- 스트레스 테스트 중요
**4.2.2      ****웹 기반 테스트
**- 자동화된 스크립트 테스트
- 응답속도와 트래픽 폭주 등의 서버 부하의 스트레스테스트
- 네트워크 대역폭 고려
- Ajax의 경우 페이지가 변경이 안되어 자동화 테스트에 어려움
- 자동화 도구 :
STAF은 1998년 IBM에서 개발된 분산환경 테스트 자동화를 위한 프레임워크
**4.2.3      ****알파/ 베타 테스트**
- 유저를 대상으로 한 테스트 : 알파의 경우 사내/ 베타는 클로즈와 오픈으로 나눔
- 알파 테스트 : 막바지 시스템의 기능적 동작 테스트 측면
- 클로즈 베타 테스트 : 파워유저들의 반응 조사, 소규모 스트레스 테스트
- 오픈 베타 테스트 : 대규모 스트레스 테스트, 시장 상황을 파악하기 위한 목적
**4.2.4      ****트랜잭션 로그 기반 테스트**
**- **데이터베이스의 단위 테스트
: 테스트 이후 스키마의 무결성 보장 확인
- 트랜잭션 프로세싱 시간
- 트랜잭션 양
- 스크립트 기반으로 자동화

**5.     ****테스트의 어려움과 해결책**
-       테스트에 대한 관심 낮음 => 교육, 프로세스로 정착화
-       형식 적인 테스트 => 테스트 품질 검사 도입
-       단순 반복의 테스트 업무 => 자동화 도구 도입
-       전문 테스터 부재 => 전문 테스트 팀 구성

**6.     ****테스트의 발전 방향**
-       자동화
-       전 SDLC 단계에 적용
-       다양한 환경의 전문가 요구

**2. Value of Software Testing**
-       Definition of Testing: The process of executing a program with the intent of finding defects.
-       Improves software quality
-       Eliminates or reduces side effects caused by software additions or modifications in advance.
**3. Principles of Software Testing**
-       Requirements Traceability: Defects originate from failing to meet customer requirements.
-       Test planning begins the moment the requirements model is complete.
-       Pareto Principle: 80% of all defects arise from 20% of the vulnerabilities.
-       Testing moves from smaller parts to larger parts.
-       Exhaustive testing is impossible.
-       Independent third-party testing is more effective.
**4. Types of Testing**
**4.1 Testing in SDLC**
**4.1.1 Testing in the Waterfall Model**
- [ Analysis – Design – Implementation – Testing – Acceptance - Maintenance ]
- Testing phase exists after implementation.
- If testing is only performed in the testing phase, it's difficult to find problems during analysis, design, and implementation.
 
*** Big Bang Testing [Simple Integration]**
 - Each module is unit tested individually.
 - No consideration for interfaces between modules.
 - All modules are combined at once after individual unit testing is complete.
 - Inefficient for large-scale systems.
 - If strange results occur when testing the program after combining all modules at once, it's difficult to identify which module is the cause, meaning all modules must be investigated.
 - Used for small-scale programs where module structure is well-designed and interfaces are not complex.
 
**4.1.2 Testing in the V-Model**
- Looks like the Waterfall model folded in half.

 Requirements Analysis -------------------------------- Acceptance Testing  --> Maintenance – Regression Testing
System Design ----------------------- System Testing
Architecture Design ------------- Integration Testing (Black Box Testing)
Module Design -------- Unit Testing (White Box Testing)
Coding – Debugging [Implementation]
 
  -  Appropriate testing is performed at each stage through requirements analysis.
 
 
**4.1.2.1. White Box Testing**
-  Also called WhiteBox/Glassbox testing because it understands internal flow.
-  A test design method that uses the control structure of procedural design for testing.
-  Useful for unit testing because it emphasizes efficiency and examines internals in relatively detail.

| Basic Path Testing | Measures complexity, verifies intended flow operation | Flowchart notation, cyclomatic complexity, test case derivation, graph matrix |
| --- | --- | --- |
| Control Structure Testing | Identifies logical errors | Logical operators, logical variables, logical parentheses, relational operators |
| Loop Testing | Verifies suitability of loop structure | Simple, nested, concatenated, unstructured loops |

**4.1.2.2. Integration Testing and Black Box Testing**
- A test design method that uses only the input and output values of the test target.
- Focuses on system reliability.

| Type | Description | Example |
| --- | --- | --- |
| Equivalence Partitioning | Testing by dividing test situations into fixed units | Testing a web server for 48 hours in 1-hour increments |
| Boundary Value Analysis | Testing changes around boundary values where the system changes | Focused testing 1 minute before and after 0:00 when the date changes |
| Graph Analysis | Analyzing graphical variations of the overall test situation | Analyzing user response time graph variations over 48 hours |
| Heuristic Techniques | Identifying empirically abnormal situations | Checking for SQL Injection, one of developers' habitual mistakes |

**4.1.3 Test Classification by Purpose**

| **Test** | **Purpose** | **Example** |
| --- | --- | --- |
| Regression Test | Analyzing the impact of changes after SW modification | Re-requesting QA after changes - Automated testing is needed as costs increase over time |
| Stress Test | Purpose of determining the available performance of software | Virtually increasing the number of concurrent users to the limit to measure system's maximum performance |
| Recovery Test | Preparation for abnormal situations, emergencies | Disconnecting the network of some distributed servers and checking if the disconnected distributed servers become available again when the network reconnects |
| Mutation Test | Analyzing types of potential defects | Modifying code and succeeding if a reaction to the modification is found during the execution of that code |

**4.2 Special Tests**
4.2.1 **Embedded SW Testing**
- HW-dependent testing required.
- Environment-specific testing required.
- Occurs when SW testing is done while HW development is not yet complete (Testing under Emulator environment).
- Not only existing Application SW but also Middleware and Hardware API need to be tested.
- If testing fails, SW patching is difficult, and there is a possibility of recalls.
- Stress testing is important.
**4.2.2 Web-based Testing**
- Automated script testing.
- Stress testing for server load such as response speed and traffic congestion.
- Consideration of network bandwidth.
- In the case of Ajax, automated testing is difficult because pages do not change.
- Automation Tools:
  STAF is a framework for distributed environment test automation developed by IBM in 1998.
  NTAF: NHN's open-source test framework license (GPL2).
**4.2.3 Alpha/Beta Testing**
- User-targeted testing: Alpha is internal/Beta is divided into closed and open.
- Alpha testing: Focuses on functional operation testing of the final system.
- Closed Beta testing: Investigating reactions from power users, small-scale stress testing.
- Open Beta testing: Large-scale stress testing, aimed at understanding market conditions.
**4.2.4 Transaction Log-based Testing**
- Unit testing of databases.
: Verifying schema integrity after testing.
- Transaction processing time.
- Transaction volume.
- Automated based on scripts.
 
**5. Challenges and Solutions in Testing**
-       Low interest in testing => Education, institutionalization as a process.
-       Formalistic testing => Introduction of test quality inspection.
-       Simple repetitive testing tasks => Introduction of automation tools.
-       Lack of professional testers => Formation of a specialized test team.
