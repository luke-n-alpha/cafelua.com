**2.     ****개발 방법론의 역할**
-       문제를 푸는 반복적인 패턴
-       표준화 : 이해 당사자간의 이해 용이
-       구조화 : 문제를 구조화 시켜 이해와 풀이가 용이
-       재사용성 향상 : 산출물의 재사용성을 높이는데 기여
**3.     ****개발 방법론의 구성**
-       단계 : 개발 방법론은 개발 과정을 시간 순으로 단계를 나누어 접근
-       시간 : 개발 방법론이 수행 되는 비용
-       활동 : 각 단계별 활동을 명시
-       산출물 : 활동별 필요 산출물
-       개발기법 : 개발시 지향하는 설계 관점
-       이해당사자(조직) : 개발방법론을 수행하는 주체
**4.     ****개발 방법론의 종류 및 발전 : 재사용성을 높이기 위한 방향으로 발전**
-       **구조적 개발 방법론 (Process Oriented Methodology)**
:  시기 : 1970년대
:  관점 : 기능 중심
:  SDLC의 폭포수 모델이 기본
:  분할과 정복의 원칙
:  낮은 재사용성
-       **정보 공학 방법론 (Data Oriented Methodology)
**:  시기 : 1980년대
:  관점 : 데이터 중심
:  데이터베이스 모델링에 유용
:  기능적 요소 비고려
-       **객체 지향 방법론 (Object Oriented Methodology)
**:  시기 : 1990년대
:  관점 : 객체 중심
:  기능(Behavior)와 데이터(Attribute)형태로 객체에 녹아 들음
:  캡술화, 추상화, 상속성, 다형성
:  재사용성이 높아졌으나 구현이 어려움 (주로 구현시의 개념)
:  개발언어에 종속적
-       **컴포넌트 기반 방법론 (Component Based Methodology)
**:  시기 : 2000년대
:  관점 : 컴포넌트 중심
:  블랙박스 형태의 인터페이스를 중시한 (런타임) 객체
:  OOP와 CBD는 상호 협력적인 관계, 각 컴포넌트는 OOP로 개발 가능
:  원격 프로시져로 호출되는 객체를 컴포넌트로 통칭하기도 함
:  개발 언어에 비종속적
-       **개념 지향 방법론 (Aspect Oriented Methodology)
**:  시기 : 2000년 이후
:  관점 : 핵심관심(비즈니스 로직)과 횡단관심(로깅, 보안, 트랜잭션등 공통 적용)
:  복잡한 시스템에서 분산, 혼재되는 OOP의 구현이 어려워 등장
: 횡단관심사(Advice)와 핵심관심사(Code)를 분리하여 Weaving과정을 통해 Point-cut을 만들어 시스템 구축
-       **Agile 방법론**
: 특징 :
-> 고객과의 직접적인 피드백 활동
-> 짧은 Phase를 가지며, 변화에 주저하지 않음
-> 산출물에 의존적이지 않음
-> 특정 단계과정 뿐만 아니라 개발과정중 발생할 수 있는 인적 활동도 포함
: 종류
l  XP
- 소규모 개발에 적합, 고객과의 피드백 중시
- 주요 활동 : Code Review, TDD, Pair Programming 등
l  UP
- 대규모 프로젝트에 적합
- 단계별 활동이 명확하지 않으나 주요과정은 존재
- Rational Unified Process를 묘사하는 Rational Software사의 응집되고 잘 만들어진 웹 기반 서류 집합인 RUP로 대체되어 표현
l  SCRUM
- 이슈 사항들을 Clear 할 때, SCRUM에서 제거,
- 주마다 확인
- 가시성 높음
l  SPRINT
- 한달간의 짧은 SPRINT 구성
- 회의는 15분내 주마다 확인
-        **서비스 지향 방법론 (Service Oriented Methodogy)
:  **시기 : 2000년 이후
:  관점 : 서비스 중심
:  비즈니스의 유저적 측면의 재사용성을 위한 서비스 단위 설계
:  웹기반으로 이기종간의 호환성 고려
:  SOA

**5.     ****아키텍처와 프레임워크, 개발방법론의 비교**
-       아키텍처 : 실제 구체화된 시스템의 구조
-       프레임워크 : 소프트웨어의 반제품, 프레임워크를 기반으로 프로그램을 구현
- 프레임워크는 방법론과 아키텍처를 기반으로 만들어진 반제품 소프트웨어
-       개발방법론 : 소프트웨어를 구현하는 정형화된 활동 방법

**6.     ****함수, 클래스, 객체, 패키지, 컴포넌트, 인터페이스, 서비스**
-       함수 : 소프트웨어의 구현시 입출력이 가능한 최소화된 기능 단위
-       클래스 : 객체에 대한 명세로 데이터의 Attribute와 함수의 Behavior로 이루어지며 실세계의 객체를 모델링 하기 위한 개념
-       객체 : 클래스가 실체화된 개념, 런타임시의 클래스
-       패키지 : 클래스의 묶음, 사용자 관점의 클래스의 집합이며 소속을 나타내기도 함
-       컴포넌트 : 인터페이스를 가진 런타임시의 객체로 언어에 무관한 프로시져
-       인터페이스 : 컴포넌트의 기능을 호출하기 위한 함수 규약
-       서비스 : 비즈니스 사용자 관점의 기능적 단위

**7.     ****개발 방법론 적용의 이슈**
-       형식적 문서화 배제 : 교육, CMMi도입
-       방법론의 맹신 배제
-       적합한 방법론 선택
-       각 방법론과 현 업무 도메인의 특성 이해
-       방법론의 커스터마이징
-       다수의 방법론을 적절히 동시에 사용 가능
: 상호보완적인 방법론들의 예시
- Service는 Component들로 구현하고
- Component의 구현은 Class로
- Class의 구현 범위 선택은 AOP를 이용할 수 있음
- DataBase 모델링은 정보공학적방법론 이용
- Class의 Method구현은 구조적방법론 이용
- 개발 활동은 TDD와 PairProgramming, Code Review로 XP 이용

**2. Role of Development Methodology**
- Repetitive pattern for solving problems
- Standardization: Easy understanding among stakeholders
- Structuring: Structures problems for easier understanding and solution
- Improved reusability: Contributes to increasing the reusability of deliverables
**3. Components of Development Methodology**
- Stages: Development methodology approaches the development process by dividing it into chronological stages.
- Time: Cost incurred for performing the development methodology.
- Activities: Specifies activities for each stage.
- Deliverables: Necessary deliverables for each activity.
- Development Techniques: Design perspective aimed for during development.
- Stakeholders (Organization): Entities performing the development methodology.
**4. Types and Evolution of Development Methodologies: Evolved towards increasing reusability**
- **Structured Development Methodology (Process-Oriented Methodology)**
: Period: 1970s
: Perspective: Function-centric
: Based on the SDLC Waterfall Model
: Principle of Divide and Conquer
: Low reusability
- **Information Engineering Methodology (Data-Oriented Methodology)**
: Period: 1980s
: Perspective: Data-centric
: Useful for database modeling
: Functional elements not considered
- **Object-Oriented Methodology (Object-Oriented Methodology)**
: Period: 1990s
: Perspective: Object-centric
: Functions (Behavior) and data (Attribute) are embedded in objects.
: Encapsulation, Abstraction, Inheritance, Polymorphism
: Increased reusability but difficult to implement (mainly a concept during implementation)
: Dependent on development language
- **Component-Based Methodology (Component-Based Methodology)**
: Period: 2000s
: Perspective: Component-centric
: Emphasizes black-box interfaces (runtime) objects
: OOP and CBD are mutually cooperative, each component can be developed with OOP.
: Objects called by remote procedures are sometimes collectively referred to as components.
: Independent of development language
- **Aspect-Oriented Methodology (Aspect-Oriented Methodology)**
: Period: After 2000
: Perspective: Core concerns (business logic) and cross-cutting concerns (logging, security, transactions, etc., commonly applied)
: Emerged due to the difficulty of implementing distributed and intertwined OOP in complex systems.
: Separates cross-cutting concerns (Advice) and core concerns (Code) to build a system through a Weaving process that creates Point-cuts.
- **Agile Methodology**
: Features:
-> Direct feedback activities with customers
-> Short phases, not hesitant to change
-> Not dependent on deliverables
-> Includes human activities that may occur during the development process, not just specific stages.
: Types
l XP
- Suitable for small-scale development, emphasizes customer feedback
- Key activities: Code Review, TDD, Pair Programming, etc.
l UP
- Suitable for large-scale projects
- Stage-specific activities are not explicit, but key processes exist.
- Replaced by RUP, a cohesive and well-crafted web-based documentation set from Rational Software, describing the Rational Unified Process.
l SCRUM
- When issues are cleared, they are removed from SCRUM.
- Weekly check-ins
- High visibility
l SPRINT
- Short SPRINTs of one month
- Meetings are weekly, within 15 minutes.
- **Service-Oriented Methodology (Service-Oriented Methodology)**
: Period: After 2000
: Perspective: Service-centric
: Service-unit design for reusability from a business user perspective.
: Web-based, considering compatibility between heterogeneous systems.
: SOA

**5. Comparison of Architecture, Framework, and Development Methodology**
- Architecture: The structure of an actual, materialized system.
- Framework: Semi-finished software; programs are implemented based on the framework.
- A framework is semi-finished software built upon methodologies and architecture.
- Development Methodology: A formalized set of activities for implementing software.

**6. Function, Class, Object, Package, Component, Interface, Service**
- Function: The smallest functional unit with input/output possible during software implementation.
- Class: A specification for an object, consisting of data Attributes and function Behaviors, a concept for modeling real-world objects.
- Object: A materialized concept of a class, a class at runtime.
- Package: A collection of classes, a set of classes from a user's perspective, also indicating belonging.
- Component: A runtime object with an interface, a language-independent procedure.
- Interface: A function contract for calling the functionality of a component.
- Service: A functional unit from a business user's perspective.

**7. Issues in Applying Development Methodologies**
- Exclusion of formal documentation: Education, CMMi adoption
- Avoid blind faith in methodologies
- Selection of appropriate methodology
- Understanding the characteristics of each methodology and current business domain
- Customization of methodologies
- Multiple methodologies can be used appropriately and simultaneously.
: Examples of complementary methodologies
- Services are implemented with Components.
- Components are implemented with Classes.
- The scope of Class implementation can be selected using AOP.
- Database modeling uses information engineering methodology.
- Class Method implementation uses structured methodology.
- Development activities use XP with TDD, Pair Programming, and Code Review.
