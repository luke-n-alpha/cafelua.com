**3. 네이버 ME의 모바일 페이지의 현황**
** 1) 네이버 ME는 모바일까지 고려했다 ?**
네이버 오피스의 경우에 보듯, 사실 브라우져를 구분해서 거부하거나 모바일페이지로 보내는것은 얼마든지 가능한 상황입니다. 하지만 네이버 ME는 이를 구분해두지 않았을 뿐만 아니라 기능도 정상 동작합니다. 이는 모바일페이지의 가능성이 이미 여기까지 와 있음을 여실히 보여주는 것이 아닐까 합니다.

** 2) 레거시 시스템들의 한계**
그러나 위의 경우에서 보았듯이 네이버ME는 기존의 메일과 각종 다른 서비스들의 집합체입니다. 기존의 레거시 시스템 곧곧에는 문제점들이 보이고 있으며, 이는 현존하는 모든 웹서비스들이 가지고 있는 문제일겁니다. 결국은 이는 비용을 발생시킬것이고, 웹표준 문제를 더욱 불거지게 하겠죠.

**4. 모바일 브라우징의 개선 필요**
** 1) 드래그인 드롭과 마우스오른쪽 액션의 대체 기능및 브라우져 개선 필요**
무엇보다도 위의 테스트 과정중 몇가지 테스트를 하고 싶었으나 불가능했던 부분이 있었는데, 바로 RIA의 꽃인 드래그앤 드롭과 마우스오른쪽키에 대한 테스트 불가능이었읍니다. 이를 지원하는 브라우져가 있는지 궁금하더군요. 네이버앱이나 다음앱의 경우 내부에 브라우져를 내장하고 있는 형태니 차후에 브라우져에 해당 기능이 들어가면 어떨까 하는 부분이었습니다.
혹은 아예 이 기능들은 배제하고 새로운 액션으로 대체해야겠죠. 그러나 드래그앤드롭은 다른 앱에서도 많이 사용되는 액션으로 모바일웹에서 굳이 제외시키는것은 좋아보이지는 않습니다. 브라우져의 지원을 기대합니다.

** 2) JavaScript엔진 속도의 개선 필요**
PC환경보다 확실히 느립니다. 어째서 구글이 크롬브라우져를 발표할때마다 사파리에 비해 Javascript엔진이 몇배가 빠르다는것을 강조했는지를 알 수 있는 부분입니다. RIA에 가까워질 수록 Javascript엔진 처리는 중요해집니다.

Yesterday, Naver ME opened, and I uploaded a [post](http://fstory97.blog.me/70099012785) I had written during the [CBT](http://fstory97.blog.me/70099012785). On that post, [ib소년](http://skylark970.blog.me/) commented, saying that Naver ME should be light enough to be viewable on mobile. So, while I was at it, I tried accessing it on mobile. Previously, during the CBT, accessing it on mobile would lead to Naver ME's introduction page, so I hadn't been able to test this.
The result? It works! Ta-da~

**1. Naver ME Mobile Test. Very Good!**
{{IMG:1}}
**[ Naver ME displayed well / Browser used: Dolphin HD ]**

The layout was mostly intact, and I could even write posts on Me2day or send notes without much trouble (?). Of course, the loading time was long, and when writing posts on Me2day, there was a noticeable delay, possibly due to JavaScript operations. I tested it on 3G, and it showed normal operation. The Optimus Q has a 3.8-inch screen with 800-series resolution, so I had to zoom in a bit to see it clearly. Even if it were Retina, the font is indeed too small considering the physical size.

**2. What about existing systems?**
**1) Mail List: Layout is broken, but acceptable**
{{IMG:2}}
I tested mail instead of Naver ME. To perform actions accurately, I zoomed in with a double pinch. The layout was a bit broken, but moving between categories was fine.
{{IMG:3}}
Tested Daum too... it also works well.

**2) But the doomed RIA Editor**
But when I clicked 'Write Post,' a message appeared asking me to install Flash. Unfortunately, the Optimus Q is still on 2.1, which doesn't support Flash.
After that, if I retry, the RIA editor appears normally. However, I couldn't actually write anything in the RIA editor.

**3) What about Naver Word? ******

{{IMG:6}}

**3. Current Status of Naver ME's Mobile Page**
**1) Did Naver ME consider mobile?**
As seen with Naver Office, it's entirely possible to differentiate browsers and either deny access or redirect to a mobile page. However, Naver ME not only doesn't differentiate but also functions normally. This clearly demonstrates how far the potential of mobile pages has come.

**2) Limitations of Legacy Systems**
However, as seen in the cases above, Naver ME is a collection of existing mail and various other services. Problems are visible throughout the existing legacy systems, and this is likely an issue faced by all current web services. Ultimately, this will incur costs and further highlight web standards issues.

**4. Need for Mobile Browsing Improvement**
**1) Need for alternative functions for drag-and-drop and right-click actions, and browser improvement**
Above all, during the testing process, there were some things I wanted to test but couldn't, specifically the inability to test drag-and-drop and right-click, which are the hallmarks of RIA. I wondered if there was a browser that supported these. In the case of Naver App or Daum App, they have built-in browsers, so I wondered what it would be like if these features were included in the browser later. Or, these functions might need to be excluded entirely and replaced with new actions. However, drag-and-drop is an action widely used in other apps, so excluding it from mobile web doesn't seem ideal. I hope for browser support.

**2) Need for JavaScript Engine Speed Improvement**
It is definitely slower than a PC environment. This makes it clear why Google emphasized that its JavaScript engine was several times faster than Safari's whenever it announced the Chrome browser. As it gets closer to RIA, JavaScript engine processing becomes more important.

**3) Mobile H/W: Higher Resolution, Faster CPU**
Fortunately, phone specs are evolving very rapidly, so they will soon approach PC capabilities without difficulty. However, based on my current experience, it's still too early. But the mere fact that it works suggests it will soon be widely adopted in a very short time. And I think the resolution will eventually be standardized around 1024. This is because most of the current web is based on a horizontal size of 1024, established during the 14-15 inch monitor era. In other words, my current 3.8-inch screen still feels a bit small. While I thought 4 inches was too big at one point, I've come to the conclusion that as high-resolution devices increase in the future, 4-inch screens will inevitably become the norm.

**5. The Potential of Mobile Web and HTML5**
It is my personal opinion that mobile web will eventually replace a significant portion of mobile apps. I believe that time will come when devices with 1024 resolution, 4G network environments supporting stable performance QoS, and Atom-class CPU performance are released. If I just say this, it's actually expected that such an environment will be established in a very short time (within at least 3 years). What form should our web services take by then? HTML5 will certainly grow in importance for mobile. And I believe web platforms will be at its core. Perhaps then, web OS like Chrome OS will also gain momentum.
