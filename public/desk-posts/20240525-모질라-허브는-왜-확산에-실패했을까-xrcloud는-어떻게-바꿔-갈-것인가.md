안녕하세요.  숲속얘기 입니다. 빌리버의 루크라고 해야 할까요? 영문 포스팅도 함께 진행해야 해서 필명에 관해서는 아직 정리를 좀 해야 할것 같네요.  모질라허브 서비스 종료와 팀 해체에 대한 공지를 알릴때, 한국 정부(정보통신산업진흥원)의 오픈소스 과제 제안을 진행했다 실패했다고 알렸었죠? 해당 제안서에는 모질라 허브의 기존 약점과 함께 향후 발전 시키기 위한 계획이 포함되어 있었습니다.  모질라허브 서비스가 완전히 종료되는 5월 31일 전에 해당 내용을 공개해야 모질라허브를 개발했던 전세계의 개발자들의 의견도 좀 들을 수 있을 것 같아 모질라 허브 프로젝트의 약점과 XRCLOUD의 방향성에 대해 공개 합니다.​ 아래의 내용들은 저희 퇴사한 내부 팀원들의 논의들을 정리한 것으로 저 혼자만의 생각이 아닌 점은 미리 밝힙니다.​

**1. 모질라 허브 프로젝트의 약점**

{{IMG:1}}

힙스터 언어라는 Elixr

- - **2D/3D 프론트엔드와 백엔드의 통합 소스 구조 문제**- Hubs의 코드는 프론트엔드는 A-frame기반의 3D가 가장 특징이지만, 2D의 코드도 있고, 최근 모던 프로젝트들 처럼 백엔드가 별도로 분리되어 있지 않아 코드 유연성이 떨어지며, 개발자 수급이 어려움
- **동시 접속자 수 제한 **- Hubs의 어드민 서비스내에는 40명까지 인원수 제한이 있었으나, 실제 필드 테스트 결과 25명이 제한이 걸림, 이유는 안드로이드의 WebRTC이슈와 함께 모든 사용자의 목소리와 액션 이벤트 상황 WebRTC서버가 중개해야했기 때문에 WebRTC서버의 네트워크 Bandwidth가 넘쳐버리는 문제 때문이었음
- **스포크 에디터와 블랜더 기반의 창작도구의 한계**- 웹에디터 스포크는 허브의 가장 큰 특징이며, 이를 이용한 교육프로그램들이 많이 만들어짐에 따라 확산에도 가장 큰 기여를 하였음.
- 하지만 스포크 프로젝트의 관리는 미진하여 버그가 많고, 게임엔진 처럼 고난이도 서비스를 하기에는 부족함.
- 이를 해결하기 위해 허브의 오픈소스 그룹은 오픈소스 그래픽 도구인 블랜더의 플러그인을 웹에디터의 스포크를 대체하고자 하는 프로젝트가 진행 중임. 하지만 이 경우 스포크를 사용하던 가벼운 유저와 웹 콘텐츠 관리자 수준의 관리가 되던 장점은 포기하게 됨. 결론을 얘기하자면, 가벼운 유저의 창작 도구로서의 방향은 포기하고 있어 이에 대한 대책이 필요함
- 또 하나의 이로인한 구조적인 문제는 에디터와 플레이어의 소스 분리로 인해 창작할때와 플레이할때의 품질과 기능이 차이가 생기는 발생함.
- **대중적이지 않은 피닉스 기반의 레티큘럼 기술 사용으로 인해 진입의 어려움**- Hubs는 모든 이벤트들은 Hubs를 위해 개발된 Reticulum이라는 별도의 웹서버를 통해 중계 관리하여 중추적인 역할을 맡고 있음
- 그런데 이 Reticulum웹서버는 Phoenix웹서버 프로젝트의 파생으로 Elixir와 Erlang이라는 대중적이지 않은 언어로 개발되었음
- 결국 이를 위 신규 학습이 필요한데, 개발자들의 경력관리에서 선택되기 어려운 언어임
- 결과적으로 개발자들의 모질라허브 오픈소스 참여에 가장 큰 장벽으로 작용하고 있어 왔으며 빌리버내에서도 프로젝트 파악에 가장 걸림돌이 되어왔음
- **튜링완전성 미달로 게임 구현 불가**- 많은 메타버스 프로젝트들은 게임에서 시작했기 때문에 이와 비교를 받았고 메타버스붐 시절에도 불구하고 비교 우위 미달로 확산에 장애가 됨
- **그래픽 품질 미달**- WebXR프로젝트들이 강력한 쉐이더 엔진과 이펙트들을 지는 게임엔진대비 지적되는 사항

**2. 문제점별 XRCLOUD의 현황 및 향후 계획**

**2-1. 2D/3D 프론트엔드와 백엔드의 통합 소스 구조 문제**

- - - **접근 방법과 완료 한 것**- XRCLOUD라는 Wraping한 API프로젝트를 개발하고, XRCLOUD를 이용할 수 있는 별도의 프로젝트를 Nest.js의 backend와 Next.js의 frontend로 분리하여 개발하여 유연성을 증가시키고 기능적으로는 워드프레스의 초급 CMS수준까지 끌어올렸음. 또한  각 프로젝트 배포는 모두 docker로 가상화 시키고 이 프로젝트를 Hubs all In One이라는 별도의 프로젝트로 만들어 통합 관리하게 함, 이를 통해 프레임워크에만 익숙한 초급 개발자도 개발/배포가 쉽게 가능하도록 구조 변경했음
- 2D레이어에 iframe 웹브라우징 영역을 개발하고 3D영역과의 데이터를 주고 받을 수 있도록 개발을 진행하였음. 이를 통해 기존 웹플랫폼과 3D메타버스 공간간의 상호 운용성이 크게 증가하게 됨. 하지면 현재 XR환경에서는 동작시키지 못함
- 해당 Nest.js와 Next.js 프로젝트 backend forntend코드는 현재 아웃소싱을 주고 있는 파트너들에게만 정리해서 프로젝트 소스와 레파지토리를 전달하여 자체 개발 하도록 하고 있음
- **향후 할 것**- **백엔드, 프론트엔드의 코드 정리 **- 다수의 아웃소싱 프로젝트를 수행함에 따라 백엔드, 프론트엔드 코드가 프로젝트 별로 기능이 좀 다르게 구현되어버려 통합 소스를 만들어 가장 강력한 소스를 만들 필요가 있음
- **XR경험시 2D웹브라우징 영역의 3D에셋 통합**- XR디바이스에도 가능하게 변경 진행 예정, 파트너 개발사(테크빌)에서 3D공간내에 iframe배치가 성공했다고 하니 통합이 가능 할 것으로 예상됨
- **소스의 오픈소스화 혹은 XRCLOUD대시보드 통합**- 해당 서비스 레이어의 소스를 오픈소스화 하여 XRCLOUD의 사용 확산을 꾀할 수 있음
- 더 초급 개발자 혹은 유저들을 위해서는 XRCLOUD내에 GUI 대시보드로 만들어 위즈윅 서비스 수준으로 끌어올리는 것도 방안이나, 현재 1인 프로젝트로 진행함에 있어서는 갈 방향은 아니어서 고려하지 않음

**1. Weaknesses of the Mozilla Hubs Project**

{{IMG:1}}

The "hipster language" Elixir

- - **Problem with Integrated Source Structure for 2D/3D Frontend and Backend**
    - Hubs' code is characterized by its A-frame-based 3D frontend, but it also has 2D code. Unlike recent modern projects, the backend is not separately decoupled, which reduces code flexibility and makes it difficult to secure developers.
- **Limited Concurrent Users**
    - Hubs' admin service had a limit of 40 concurrent users, but actual field tests showed a limit of 25 users. The reason was an Android WebRTC issue, combined with the problem of the WebRTC server's network bandwidth being overwhelmed because it had to mediate all users' voices and action events.
- **Limitations of Spoke Editor and Blender-based Creation Tools**
    - The web editor Spoke is a major feature of Hubs and has contributed significantly to its spread as many educational programs were created using it.
    - However, the Spoke project's management has been insufficient, leading to many bugs, and it's inadequate for high-level services like game engines.
    - To address this, Hubs' open-source group is working on a project to replace the Spoke web editor with a Blender plugin, an open-source graphics tool. However, this means abandoning the advantages of Spoke for casual users and web content managers. In conclusion, the direction for casual user creation tools is being abandoned, and a solution is needed for this.
    - Another structural problem arising from this is the difference in quality and functionality between creation and playback due to the separation of editor and player sources.
- **Difficulty of Entry Due to Use of Unpopular Phoenix-based Reticulum Technology**
    - All events in Hubs are mediated and managed through a separate web server called Reticulum, developed for Hubs, playing a central role.
    - However, this Reticulum web server is a derivative of the Phoenix web server project and was developed using unpopular languages like Elixir and Erlang.
    - Consequently, new learning is required, but these are languages that developers find difficult to choose for career management.
    - As a result, it has been the biggest barrier to developers' participation in the Mozilla Hubs open-source project and has been the biggest obstacle to understanding the project within Belivvr.
- **Inability to Implement Games Due to Lack of Turing Completeness**
    - Many metaverse projects started as games, so Hubs was compared to them. Despite the metaverse boom, its lack of comparative advantage hindered its widespread adoption.
- **Poor Graphic Quality**
    - A point of criticism for WebXR projects compared to game engines with powerful shader engines and effects.

**2. XRCLOUD's Current Status and Future Plans by Problem**

**2-1. Problem with Integrated Source Structure for 2D/3D Frontend and Backend**

- - - **Approach and What Has Been Completed**
        - Developed a wrapping API project called XRCLOUD, and separated projects that can use XRCLOUD into a Nest.js backend and a Next.js frontend to increase flexibility and functionally elevate it to the level of a basic WordPress CMS. Also, all project deployments are virtualized with Docker, and these projects are integrated and managed as a separate project called "Hubs All In One." This structural change makes development/deployment easy even for beginner developers familiar only with frameworks.
        - Developed an iframe web browsing area in the 2D layer and enabled data exchange with the 3D area. This significantly increases interoperability between existing web platforms and 3D metaverse spaces. However, it currently does not work in an XR environment.
        - The Nest.js and Next.js project backend/frontend code is currently being organized and delivered to our outsourcing partners for their own development.
    - **What to Do Next**
        - **Backend, Frontend Code Refinement** - As multiple outsourcing projects have been carried out, backend and frontend code functionalities differ slightly per project, so there is a need to create a unified source to build the most robust source.
        - **Integration of 2D Web Browsing Area into 3D Assets for XR Experience** - Planned to be changed to work on XR devices. Since our partner developer (Techvill) has successfully placed iframes within 3D space, integration is expected to be possible.
        - **Open-sourcing the Code or Integrating into XRCLOUD Dashboard** - Open-sourcing the code of this service layer can promote the widespread use of XRCLOUD.
        - For more beginner developers or users, creating a GUI dashboard within XRCLOUD to elevate it to a WYSIWYG service level is an option, but it's not the direction to go for a current one-person project, so it's not being considered.
