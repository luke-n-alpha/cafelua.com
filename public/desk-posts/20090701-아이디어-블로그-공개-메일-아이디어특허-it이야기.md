**1.   ****제목 : 블로그 공개 메일함**
-      배경 : 메일을 블로그에 편입하는 단순한 컨버젼스에서, 블로그가 가지고 있는 댓글과 답글의 피드백 기능을 활용하며, 주소록의 그룹과 연동하여 그 활용 범위를 높이는 목적에 의한 아이디어
-      효과 : 용량 제한의 폐지 (1기가, 6기가 용량 제한 없음, 블로그와 같이 영속적)
이메일의 활성화
주소록의 그룹단위의 웹메일 이용 용이
블로그를 통한 이메일 접근성 강화
개인 웹진의 손쉬운 발행으로, 새로운 서비스 모색
- 최초 작성일 : 2008년 07월 24일

**2.8) 외부 메일에 보내는 공개 메일**

- 외부 메일에는 메일 표준 스펙내에서 주지시켜야 한다.
- 이는 제목과 서명 기능을 이용한다.

라는 내용을 첨부한다.
* 송신자 공개 메일함의 URL을 적어도 좋다.

**2,9) 공개 메일함을 이용한 방명록 만들기**
방명록이라는 공개 메일함을 만들면, 외부 유저에게는 마치 게시판이나 방명록 처럼 보이게 된다.
이는 내용에 의한 메일을 메일함에 분리하는 것이 아니라, 송신자가 수신자의 메일함을 직접 선택하는 효과를 가져온다.
: 비공개 메일함의 경우, 기존 비공개 방명록과 동일하게 외관상 보인다.
-      방명록과의 차이점
: 유저는 답장을 받아볼 수 있도록, 반드시 이메일 필드를 채워야 한다.
블로거가 유저의 방명록(메일함)에 답글을 달면, 해당 답글은 이메일로 전송된다.
또한, 이 답장에 다시 유저가 답장을 보내면, 해당 방명록(메일함)에 답글이 달리게 된다.

2.9) 메일함 최근 답장 기능
- 위와 같은 기능을 구현 할 시, 이메일의 보존기간은 예전 방식에 비해 게시물과 같이 영속성을 갖게되고, 아주 오래전에 보내거나 작성한 메일도, 공개 메일함에서 누군가가 답글 혹은 댓글을 달게 될 수 있다. 때문에 게시물의 최근 답글, 댓글기능 처럼 최근 답장 기능을 필요로 하게 될 수 있다.

2.10) 웹진구독 신청 - 주소록이 연동된 공개 메일함을 이용해 웹진을 발행하는 행위자체만을 놓고 봤을때는, 결과적으로 싸이월드의 페이퍼 같은 개인 퍼블리싱과 비슷하며, 혹은 Usnet같은 웹진과 비슷한 결과가 만들어진다. 페이퍼와 웹진의 중간 정도라고 할 수 있겠다.
구독 신청을 하게 될 경우 기존의 웹진 신청과 비슷하게 동작하나, 이 과정은 자동으로 등록되는 것이 아니라, 유저가 신청 댓글 혹은 답장을 받아, 주소록의 그룹에 추가하는 방식 이다.
그러나 필요에 따라 기존의 웹진 구독 기능 처럼, 주소록에 유저가 입력한 이메일을 자동으로 추가하는 방법도 고려해 볼 수 있다.

2.9) POP 서버 기능 – 근본적으로 메일이기 때문에, POP 서버를 지원할 수 있다. 따라서, 타사 서비스나 다른 플랫폼에서 블로그 메일함을 조회 혹은 내용을 가져갈 수 있으며, 모바일 영역에서도 이메일과 동일한 서비스를 제공하는 확장성을 지니고 있다.

**3.   ****구현**
-      근본적으로 게시판위에 덮힌 웹메일 시스템이다.
-      이는 이메일이 단가가 비싸고, 용량 제한 같은 요소가 있기 때문이다.
-      따라서, 구현단에서는 블로그의 게시판 같은 외부 시스템에서 메일 서버를 임시 캐시로 이용하는 방식을 통하여서, 새로운 입력, 수정이 발생하는 경우에만, 메일 서버를 이용하도록 메일에 대한 의존도를 낮춘다.
**오래된 메일의 경우, 대게는 휴지통으로 이동되고, 삭제된다. 그러나 이 시스템의 경우에는 유저 몰래, 휴지통이 아니라, 게시판 서버로 이동되나, 유저가 보기에는 처음부터 게시물로 존재함으로 차이를 느끼지 못한다.**
** 만약 유저가 게시판 서버의 이전 메일에 답장을 보내는 경우, 해당 게시판 서버의 DB에저장된 메일 헤더(수신자.발신자 주소 등)의 정보를 활용하여 새로운 이메일을 생성한다**
è  그러므로 내부는 이메일과 서버는 이원화 되어있으나, 유저는 메일을 이용하고 있다는 느낌을 그대로 지니고 있어야 한다.
-      또한 현재의 시스템에서 답장이란 정보는 기존 메일 시스템에서 존재하지 않는다.
답장에 대한 정보는 그저 Re] 란 제목으로 표시 될 뿐, 기존 메일과 동일하게 취급된다.
구글의 경우,

-      **답장에 대한 정보를 알아내는 방법 :**
: 기존에는 답장이라는 것을 알아내는 수단은 Re] 제목 를 통한 방법만 사용하고 있다.
(구글의 경우)
그러나, 위의 아이디어의 경우, 제목을 변경하고, 내용을 변경한 경우도 답장임을 알아야 한다. 때문에, 공개메일의 발송자의 부모 메일 포스트의 주소 혹은 ID를 함께, 답장 시 발송을 해주어야 한다.
이를 추가로 해결하기 위해서는, 메일헤더의 메시지 ID를 이용한다. (따라서, 게시물에는 이메일의 메시지 ID가 부여된다.) 표준으로 송신측에서 원문 메시지 ID를 송신해줄 것을 요청해야 할 수 도 있다.
이 방법이 여의치 않을 경우, 내용에 숨은 html 태그나, 사용자가 볼 수 있는 내용을 삽입한다.

2)    메일 서버 : 실제로 발송, 수신을 전담하는 메일 서버
3)    게시판/포스트 서버 : 데이터를 백업 및, 유지하는 서버

**4.   ****스팸 처리의 중요성 확대**
-      메일이 영속적으로 존재함에 따라, 스팸에 의한 공격의 대상이 되었을 경우, 매우 큰 코스트를 발생 시킨다. 따라서, 이에 따른 스팸에 대한 대책이 더 확실히 있어야 한다.
-      기존 이메일 처럼 스팸을 잡아내고, 사용자가 설정 하는 기능 뿐만 아니라, 이미 기록되어 있는 스팸을 찾아내고, 혹은 유저가 확인 하지 않아 쌓이는 스팸을 제거하는 기술을 필요로 한다.

**1. Title: Blog Public Mailbox**
- Background: An idea aimed at expanding the scope of email usage by not just a simple convergence of incorporating email into a blog, but by leveraging the blog's comment and reply feedback features and linking it with address book groups.
- Effects: Abolition of storage limits (no 1GB, 6GB limits, permanent like a blog)
  Email activation
  Easy use of webmail by address book groups
  Enhanced email accessibility through blogs
  Easy publication of personal webzines, exploring new services
- First Draft Date: July 24, 2008

**2. Operation Description and UI**
**2.1) Mail Writing Screen**
{{IMG:1}}

- The basic concept is an integrated service of blog and mail.
- In addition to Blog and reviewlog, 'mail' has been added.
- System-generated inboxes / sent mailboxes / bills / trash (missing in image) are set to private.
  (Not visible to other users)
  - In the example above, 'Club' and 'Personal Mail' are mailboxes created by the user, but are set to private (default) as the user does not wish to disclose them to third parties.
  - In the case of 'Data Room' and 'Church Newsletter', they are public as the user wishes to disclose them to others.
  (Similar to blog posts, third-party writing permissions may not be available in mail categories.)
  (Others' posts may be added via replies. This is explained below.)

**3. Implementation**
- Fundamentally, it is a webmail system overlaid on a bulletin board.
- This is because email has high costs and factors like storage limits.
- Therefore, in the implementation phase, the dependency on mail is reduced by using the mail server as a temporary cache from an external system like a blog's bulletin board, only utilizing the mail server when new input or modifications occur.
**In the case of old emails, they are usually moved to the trash and deleted. However, in this system, they are moved to the bulletin board server, not the trash, without the user's knowledge, but to the user, they appear as existing posts from the beginning, so no difference is felt.**
**If a user sends a reply to an old email on the bulletin board server, a new email is generated using the mail header information (recipient, sender address, etc.) stored in the bulletin board server's DB.**
è Therefore, although the internal email and server are dualized, the user should retain the feeling of using email.
